# UI audit and targeted fixes — 16 November 2026

Branch: `migration/projects-ui-preview` (fork PR #5).

## Found and implemented

1. **Desktop preview header layout:** the preview-only Overview button incorrectly
   inherited full-width dropdown styling. Scoped a top-level navigation override
   while preserving full-width links inside dropdowns.
2. **Open nav overlays:** navigation `details` stayed expanded after selecting
   a preview screen. Close menus after navigation and on Escape; keep the
   current preview destination visually and accessibly selected.
3. **App cards leading to 404:** real `/apps/:code/launch` routes are absent
   from this branch. Show an explicit disabled launch status instead of a
   clickable link. Assigned applications are not equivalent to working SSO.
4. **Phone UI:** preview section toggles use a two-column grid, selectors
   have narrower responsive rules, and admin tabs scroll horizontally rather
   than consuming multiple rows.
5. **Authenticated Projects list:** distinct styles for refresh/load-more/empty
   state and keyboard-focusable horizontally scrollable table region.
6. **Operations state:** clearing employee filters also clears stale selected
   details; changing organizations resets member pagination. HR access search
   has an explicit empty state and result count.
7. **Project timeline:** overdue task/milestone calculation no longer uses a
   fixed November 2026 date.
8. **Login page 404:** the fork's `/accept-invite` page is in a different
   staged branch; replaced its broken link with an explicit disabled notice.
   The login form also explains when no sign-in endpoint exists.

## Important limitations

This is a **static source/UI review**, not an authenticated browser session or
pixel-diff proof. This runner cannot reach GitHub over network from the local
build container. `npm run check` and responsive browser screenshots remain
pending; source assertion tests were added but have not been executed.

Customer invitation acceptance and employee enrollment/password pages exist
separately in fork PRs #1 and #2. They have not been merged into this UI branch,
so this branch does not offer functional enrollment. Their backend contracts,
CSRF/session/MFA/permission checks also remain unverified.

The frontend preview remains synthetic and development-only. No staging
backend, production accounts, database, customer email, SSO, or organization
repository has been modified. Disabled write controls are intentional until
authorization and persistence work is ready.

## Build-discovered correction

The first TypeScript verification after integrating frontend screens exposed an
existing Outreach mode-name mismatch: the preview passed `outreach-access`
but `AccessPreview` only accepted `outreach`. It therefore rendered the Music
chooser for the Outreach screen. The union and render branch now use the same
`outreach-access` identifier and have an explicit regression test.

## CI verification script correction

The Node 24 run showed 45 source tests passing, successful `tsc`, ESLint
without errors, and a successful Next 16.4.6 production build. The old
`verify-preview-route.mjs` then failed because it only knew one manifest
location that this Next build does not emit. The script now accepts the
recognized App Router manifest locations, requires the encoded preview
page to be registered, and leaves the separate HTTP 404 check in CI.
Frozen legacy JavaScript archives are excluded from ESLint; their byte-integrity
tests still run. These changes require a fresh CI run for acceptance.

## Streaming-redirect gate

Next.js 16.4.6 can return an HTTP 200 streamed shell containing a redirect
when `redirect()` is invoked inside Suspense. The production CI previously
expected only a 302/307 response and caught this discrepancy. The frontend
now uses a Next.js `src/proxy.ts` deny-only prefilter for the three
currently protected routes. It rejects absent/malformed portal session cookies
with an immediate redirect to `/login`; the original server-side
`portalApi('/api/auth/me')` verification still runs for every syntactically
valid cookie and remains the only authority for user and tenant access.

Do not interpret proxy cookie syntax as authentication. Check revoked,
expired and cross-tenant cookies against the reviewed staging backend.

## Hydration-aware browser test correction

The initial Chromium 320px run saw owner-only options after selecting the
Customer visual role. A selected HTML value can change before React hydration
or its state update completes, so the result did not yet prove an application
permission/screen-scoping defect. The development-only preview root now exposes
non-authoritative `data-preview-role` / `data-preview-view` state markers. The
browser smoke waits for hydration and the corresponding React-rendered state
before checking available screens or overflow; screenshots now include 320px.

## Next.js development-origin fix

The hydration-aware browser smoke surfaced a blocked Next.js dev-asset request:
the page was opened at `127.0.0.1:3100` while Next's development server
expected `localhost`. Without `/_next/` scripts, static HTML controls looked
interactive to the browser driver but React never hydrated. Browser smoke now
starts the server with `-H localhost` and uses the matching
`http://localhost:3100` origin. This alters only test infrastructure, not
production CORS, trusted API origins, or a user-facing backend.

## 320px identity panel overflow

The first correctly hydrated Chromium run found a real 5px horizontal
page overflow on `Employee account & access` at 320px. The long sample
identity/email row had no flex-child shrink/wrap rule. Added scoped
`min-width:0`, word wrapping and a 360px wrap breakpoint for that identity
hero. The browser script also now captures an overflow screenshot and
reports the bounding boxes of offending elements on subsequent failures.
